# 文字ころがし

入力した文字のアウトラインがそのままコースになり、その中を赤い玉が転がる。

- **編集モード** — 文字を打って Enter で置く。ドラッグで寄せると、接したところが複合パスになって線がつながる。離せば元の独立した文字に戻る。
- **操作モード** — 字の中をクリックして玉を置き、傾けて転がす。M5Stack CoreS3 を USB でつなぐと加速度センサで操作できる。

## 動かし方

```bash
npm --prefix SourceCode/works/moji-korogashi install
npm --prefix SourceCode/works/moji-korogashi run dev
```

`http://localhost:5174`。`.claude/launch.json` に `korogashi` として登録してある。

| 操作 | |
|---|---|
| Enter | 入力中の文字を置く（1 文字ずつ独立したオブジェクトになる） |
| ドラッグ | 文字を動かす。重なると合成される |
| Delete | 選択中の文字を消す |
| Tab | 編集 ⇄ 操作 |
| クリック（操作モード） | その場所に玉を置く |
| R | 玉を消す |
| ⇄ USB（右下） | CoreS3 に接続 |
| ＋ローカル書体 | OS に入っている書体のうち、かなを持つものを一覧に足す |

センサ未接続のときは、マウスの位置が傾きになる。

## 実機

`firmware/cores3_tilt_bridge/` を CoreS3 に書き込む。

```bash
arduino-cli compile -b esp32:esp32:m5stack_cores3:CDCOnBoot=cdc,USBMode=hwcdc \
  SourceCode/works/moji-korogashi/firmware/cores3_tilt_bridge
```

```bash
arduino-cli upload -b esp32:esp32:m5stack_cores3:CDCOnBoot=cdc,USBMode=hwcdc \
  -p /dev/cu.usbmodem101 SourceCode/works/moji-korogashi/firmware/cores3_tilt_bridge
```

FQBN のオプションは、ボード名との区切りが `:`、オプション同士が `,`。
`m5stack_cores3,CDCOnBoot=...` と書くと `Invalid FQBN` で落ちる。

M5CoreS3 のボード既定値はもともと **USB CDC On Boot = Enabled**（`CDCOnBoot=cdc`）なので、
上のオプションは明示のために付けているだけ。Arduino IDE から焼く場合も
**ツール > USB CDC On Boot が Enabled** であることだけ確認する
（CoreS3 は ESP32-S3 のネイティブ USB なので、これが無いと Web Serial からポートが見えない）。

### 感度（本体で調整する）

本体の画面下半分が操作帯になっている。

| | |
|---|---|
| 左の [ − ] / 右の [ ＋ ] | 感度を 0.1 ずつ増減（0.3〜3.0） |
| 真ん中を 1 秒長押し | 1.0 に戻す |

値は本体の NVS に残るので、電源を切っても次に入れたときそのまま。展示中に PC を触らず、
本体だけで手ざわりを詰められる。

ファームは**生の加速度と感度を別々に送る**（掛けた後の値だけ送ると、ブラウザ側で
「実機が何 g 傾いているのか」が分からなくなるため）。ブラウザ側は傾きベクトルに掛けるので、
見た目の傾きと玉にかかる力が同じ値から出たままになり、二つがズレない。

感度を持たない古いファームでも動く（その場合は 1.0 として扱う）。

### 傾きの向き合わせ

傾けた向きと転がる向きが合わないときは、**操作モードでキーを押すとその場で直る**。

| キー | |
|---|---|
| X | 左右を反転 |
| Y | 上下を反転 |
| S | 縦横をいれかえる |

選んだ値は localStorage に残るので、次に開いたときもそのまま。`config.js` の
`invertX` / `invertY` / `swapXY` は初期値という位置づけになる。

`config.js` を書き換える方法だと、Vite がページを読み込み直すたびに USB がいったん切れて
つなぎ直しになる。向きは実機を持って何度も試す作業なので、キーで変えられるようにしてある。

実機の画面には加速度の値と、傾きを示す赤い的が出る。まずそこで値が動いているかを確かめる。

※ AtomS3 Lite には IMU が載っていないので使えない。CoreS3（BMI270 内蔵）を使う。

## 設計のメモ

### 複合パスを永続オブジェクトにしない

文字は最後まで独立した `Piece` のまま持ち、**接触している集まりを毎フレーム union し直して**
輪郭を導出している。合成オブジェクトを作って管理すると「離したら元に戻す」処理が要るが、
毎回導出すれば戻す処理そのものが要らない。

union の結果は、画面に描かれる線であると同時に玉が当たる壁でもある。見え方と当たりを
別々に持つとズレるので、ここは一本化してある。

速さの実測（Chrome、`nodeSpacing: 4`）:

| | union の再計算 | ドラッグ中のフレーム |
|---|---|---|
| 4 文字が合成 | 約 5ms | 60fps |
| 6 文字が全部合成（最悪ケース） | 約 16ms | 中央値 20ms ≒ 50fps |
| 操作モード（壁 999 点） | — | 中央値 16.7ms / 最大 17.9ms |

玉が転がるあいだはコースが動かないので合成も走らず、**操作モードは常に 60fps**。
重くなるのは編集中のドラッグだけなので、`Course._mayRecompute()` で
「合成にかけた時間と同じだけ休む」間引きを入れ、描画が巻き添えにならないようにしてある。
動いていない集まりは `_groupCache` で使い回す。

### 盤ごと倒す

玉だけが動いて盤が固定だと、なぜ転がっているのかが画面から読めない。そこで操作モードでは、
**キャンバスを M5Stack の画面と同じ 1 枚の板とみなして、傾けたぶんだけ倒す**（`view.js`）。

物理には触っていない。玉は板の上（2D の盤面座標）を転がったままで、計算は今までどおり。
重力は加速度ベクトルを板の面に射影したもの＝そのまま `(ax, ay)` なので、
見た目の傾きと玉にかかる力が同じ数から出ることになり、勝手に一致する。

板は平面なので、板 → 画面はホモグラフィ（3x3）1 枚で書ける。逆行列を取れば画面 → 板に
ぴったり戻せるので、倒した状態でも「字の中をクリックして玉を置く」が正しく当たる
（往復誤差は実測 0px）。

ここも一度間違えた。X 軸まわりと Y 軸まわりの 2 回転を合成すると、回転が可換でないぶんの
捻れが混ざり、「倒れた板」ではなく「ねじれた板」に見える。板の傾きは本来 1 回の回転なので、
下り方向に垂直な軸まわりに `θ = asin(|傾き|)` だけ回す。

**静止時も倒しておく。** 傾き 0 のときに板を正面から見た絵にすると、板ではなく壁に見える。
実際には板は地面に置かれていて、それを斜め上から眺めている。そこで「カメラの俯角」
（`config.js` の `view.baseAngle`）を常にかけ、そこからの差分として傾きが乗るようにしてある。

編集モードも同じ俯角で見せる。見え方が揃うし、モードを切り替えても画が飛ばない。
ただし編集モードでは傾きを乗せない（マウスの位置が傾きを兼ねているので、
ドラッグしようとカーソルを動かすと盤まで動いて掴めなくなる）。

**玉が出ているあいだは玉に寄る**（`view.followZoom`、既定 1.9 倍）。寄せは画面側のアフィン変換で、
ホモグラフィの左から掛けるだけなので、透視の分母は変わらず逆行列もそのまま取れる。
実測で、寄せた玉は画面中心とのズレ 0px・倍率ちょうど 1.9・逆射影の誤差 0px。

追従（`view.followEase`）はわざと遅らせてある。速すぎると画面が玉に張り付いて、
玉が動いているのか背景が動いているのか分からなくなる。

盤が倒れて寄っているぶん、ポインタの座標はそのままでは使えない。ドラッグもクリックも
`view.unproject()` を通して盤面座標に戻している。実測で誤差 0px
（戻さないと 72px 動かしたときに 9.8px ずれた）。

### 「線がつながる」と「玉が通れる」は別

これが作ってみて分かった一番大事なところ。

文字を寄せて輪郭が 1 本に合成されても、玉が通れるとは限らない。実測すると、
「こ」と「ろ」を重ねて union が 1 リングになった状態でも、半径 6px の玉が到達できるのは
通行可能セル 1086 のうち 232 だけだった。接触部のくびれが玉より細く、
線の上では連続していても玉には行き止まりになる。

体験としては「くっつけたのに玉が進まない」という分かりにくい失敗になるので、
`passability.js` で別に測っている。合成後の形をラスタライズ → 距離変換 → 玉の半径で収縮 →
連結成分、という手順で、「玉が通れる範囲が N か所に分かれている」と画面下に出る。

### 穴（カウンター）の扱い

2 か所で間違えたので書いておく。

1. **外周と穴の判別**を面積の符号だけでやると「国」が壊れる。囲いの中の「玉」は
   穴の中に浮かぶ実体なので、穴として引かれて消える。リングの入れ子の深さを数えて、
   偶数を外周・奇数を穴とする（`course.js` の `ringsToShape`）。

2. **壁の内向き法線**をリングの向きで場合分けすると、穴のリングで法線が反転する。
   polygon-clipping は外周と穴を逆向きに出すので、進行方向に対して常に同じ側が塗りになり、
   式は 1 つでよい。場合分けすると玉が「ろ」の輪の中などへ押し込まれ、復帰処理も
   同じ誤った法線で穴の中へ戻すため、玉が永久に塗りの外に居座る。
   いまは巻き方向の約束に頼らず、`contains()` で実際に確かめてから決めている（`ball.js`）。

### 書体

同梱書体は `public/fonts/` に `.ttf` / `.otf` を置いて `src/fonts.js` に追記する。
線が太いほどコースとして成立しやすいので、太いウェイトだけを置いている。
玉の直径に対して線が細いと画面下で警告が出る（`config.js` の `minStrokeRatio`）。

**「＋ローカル書体」** を押すと、OS に入っている書体から**かなを持つものだけ**を一覧に足す
（`localfonts.js`）。Local Font Access API を使うので Chrome / Edge のデスクトップ限定、
初回は許可ダイアログが出る。同じファミリーに複数ウェイトがあるときは、
コースとして成立しやすいよう**いちばん太いフェイスを選ぶ**。

`opentype.js` は `.ttc` と `.woff2` を読めない。macOS のヒラギノ・游ゴシック・AquaKana は
`.ttc` なので、一覧には出ても選ぶと読めない。先頭 4 バイトを見て事前に判別し、
理由を出して元の書体に戻すようにしてある（黙って失敗させない）。

#### かなを持っているかの判定

`FontData` には収録文字の情報が無いので、実際に描いて確かめている。ここは 2 回間違えた。

1. **幅の比較では判定できない。** CJK のグリフはたいてい全角 1em で、その書体が
   持っていなくても落ちた先のフォールバックがやはり 1em なので、同じ幅になる。
2. **描いた画素をそのまま比べてもだめ。** その書体が「あ」を持たないとき、ブラウザは
   別の書体で代わりに描くが、そのベースラインと大きさは主フォントの metrics に合わせて動く。
   位置ごと比べると、かなを 1 文字も持たない Zapfino が「持っている」と出た（実測 0.0475）。

いまは**外接矩形で正規化してから形を比べている**。位置のずれが消えて形だけが残るので、
欧文書体はすべて差 0、CJK 書体は 0.070〜0.156 とはっきり分かれる（しきい値 0.02）。
実測 16 書体で誤検出・見逃しとも 0、1 件あたり約 2ms。
