# KumiJi — 組み字

タイポスの**12エレメント**を3Dプリントした部品を手で並べて字を組む。
機械が読めたときだけ光が出て、そのまま保持すると**痕跡が別の場所へ移って定着する**。

## 流れ

```
1. 輪郭を検出する
2. 静止して STILL_SEC 秒たったら OCR にかける（1回だけ）
3. 読めなければ ── 何もしない。光も出ない。動かせばまた試す
4. 読めたら ── その合図として光が出て、育ちはじめる
5. そのまま FIX_SECONDS 秒保持すると ── 定着の場へ移って残る
```

**光は「そこに物がある」の合図ではなく「読めた」の合図。**
だから定着したものには必ず見出しがある。見出しのない痕跡は原理的に出ない
（`read_at` → `progress` → `fixed` の連鎖が、読めたときしか成立しないため）。

主張はこれ。

> **文字とは、部品ではなく、部品の配置である。**

同じ部品でも配置次第で別の字になるし、どれでもない何かにもなる。
そしてどれでもない何かを組んでも、機械は**最も近い規格に丸めてしまう**。

機械は読んでいるのではない。**いちばん近い規格に丸めている。**
この性質は技術的な限界ではなく、この作品が言いたいことそのもの。

## 構成

```
[15.6インチ ノングレア モニタ]  寝かせて白を全画面表示。下から光るので影が落ちない
        ↑ 部品を置く
[iPhone / Continuity Camera]   真上から撮る
        ↓
  Python + OpenCV   輪郭で「静止したか」を見る
        ↓
  切り出した画像をそのまま macOS Vision へ渡す ── 加工は切り出しだけ
        ↓
  ずらした位置に規格字を描画  ＋  http://localhost:8899 のページへ流す
```

ブラウザも WebSocket も挟まない。**Python 1プロセスで完結**させている。
既存リポジトリはブラウザ完結（opencv.js / MediaPipe JS）が作法だが、
**macOS 純正の日本語OCR がブラウザから呼べない**ので、ここだけ Python にした。

### ファイル

| | 持っているもの |
|---|---|
| `config.py` | 触るつまみ全部。`r` で走らせたまま読み直せる |
| `probe_contour.py` | 検出の素（二値化・連結成分・ROI 検出・ズーム・自動調整） |
| `recognize.py` | 読み手。Vision と IoU。**ここだけ差し替えれば認識方式が変わる** |
| `state.py` | **作品の状態機械。** 描画もカメラも OCR も知らない |
| `view.py` | **画角と写す範囲。** 実機で毎回触る層だけを隔離してある |
| `main.py` | 描画と、上の3つを繋ぐループ |
| `page_server.py` / `page/` | ブラウザへ流す SSE サーバとページ |
| `emoji_search.py` | OS の絵文字索引（既定では使わない） |
| `selftest.py` | **カメラ無しで通す自己確認。** 変更前後で挙動が変わっていないかを見る |

## 実行方法

```bash
cd SourceCode/experiments/KumiJi

# Step 1 — 輪郭が取れるか（追加インストール不要。cv2 と numpy だけ）
python3 probe_contour.py

# Step 2 — OCR と IoU を並べて測る
pip3 install --user pyobjc-framework-Vision
python3 probe_ocr.py

# Step 3 — 本体。ページも一緒に立つ
python3 main.py          # → http://localhost:8899 をブラウザで開く
```

**カメラは1プロセスしか掴めない。** 上の3つを同時に走らせないこと。

```bash
# 触ったあとの確認。カメラも照明も要らない。10秒で終わる
python3 selftest.py
```

起動したら **まず `r` を押して、モニタの画面領域だけを ROI として囲う**。
ここを省くと大津の閾値が「画面 vs 机」で割れてしまい、部品が1つも拾えない。

## 操作（probe_contour.py）

| `z` `x` | **カメラのズーム率。** 寄せてから ROI を取る |
| `h` `j` `k` `l` | 寄せる位置（左・下・上・右） |

| `-` `=` | 二値化閾値のオフセット増減 |
| `s` | 画像と各部品の数値を保存（`outputs/`） |
| `o` | 閾値を固定／大津で切り替え |

| キー | 動作 |

| `v` | **カメラを順送り**（見つかっているものを回す） |

| `a` | 画面 ROI を再検出 |

カメラを切り替えると**画角が変わるので画面 ROI を自動で取り直す**。
開けないカメラを指定しても落ちず、元のカメラのまま続く。
ズームを変えたときも同じ理由で ROI を取り直す。

**小文字がカメラ側、大文字が写す範囲側**で揃えてある。`r` で config を読み直すと
どちらも config の値に戻るので、いじりすぎたときの取り消しはこれ。

## プロジェクターで使うとき

寝かせたモニタと違い、プロジェクターは**カメラの見る範囲と映す範囲が
一致してくれない**。合わせる順番はこれ。

1. `g` で位置合わせの枠を出す。**この間は読まない**ので、枠を部品と
   取り違えて痕跡が溜まることはない
2. プロジェクター本体の向き・レンズ・台形補正で、枠を投影面にだいたい載せる
3. 残りを `Z` `X` `H` `J` `K` `L` で詰める（`OUT_RECT`）
4. `z` `h j k l` でカメラを投影面に寄せる（`CAM_ZOOM`）
5. `W` で `config.py` に書き戻す。`g` で枠を消して読み始める

### 状態機械をループから引き剥がす

`main.py` が 1076行、`main()` が 501行、`while` ループが 441行、**そのループが
39個のローカル変数を裸で持っていた**。この構造のせいで2回落ちている。

- 升の数を `cap` という名前で持ち、**カメラを潰した**
- ROI を `found` という名前で持ち、**「見つけた語」の集合を潰した**

どちらもロジックの誤りではない。名前が衝突しただけで、状態が裸で並んでいる
構造そのものが原因だった。39個あれば、次も必ず起きる。

三層に分けた。

| | 持つもの | 知らないもの |
|---|---|---|
| `state.py` の `Piece` | 配置・読み・定着・反応の移り変わり（18個） | 描画・カメラ・OCR |
| `view.py` の `View` | 画角と写す範囲（8個） | 作品の状態 |
| `main.py` | 描画と、それらを繋ぐループ | — |

`View` を分けたのは、**この層だけが実機で毎回触られる**から。プロジェクターの
位置は日によって変わるので、寄せる・ずらす・台形を直すの操作が独立していないと、
調整のたびに作品のロジックに触ることになる。

分けたことで見つかった割れ目が一つある。「同じ語はクールダウン中なら出さない」は
状態側に、「辞書に無い語は何もしない」は呼び出し側にあり、**規則が2箇所に
割れていた**。そのままだと、辞書に無い「し」が「すし」の抑止を外してしまう。
`Piece.maybe_react()` に寄せて1箇所にした。

### 変えていないことを数字で示す

構造を変えるときは、**挙動が変わっていないことを示せないと意味がない**。
`selftest.py` がそれをする。

- 時計を偽物にする（実時間だと毎回違う結果になって比べられない）
- 台本どおりの合成フレームを流す（置く→保持→微調整→作り直す→どける→また置く）
- 認識器も台本どおりに答える（Vision を呼ばない）
- **1フレームずつ画面の画素ハッシュを取る**

この引き剥がしでは 940フレームすべてが画素まで一致した。ページへ流した 10件も、
定着した4枚の順序も、移動中の矩形 1485個も同じ。
差は内部の呼び出し順だけ（定着の判断を光を描く前に移した）。

指紋は `selftest.py` の `EXPECT` に書いてある。台本を変えたらここも変える。
**変えていないのに変わったら、どこかを壊している。**

### 場が変わるたびの探索は機械にやらせる

モニタからプロジェクターへ移すだけで、「囲う → `o` で大津 → `[` を数回 →
`=` を数回」を毎回やり直していた。しかも起動のたびに失われる。
同じ探索を人が繰り返すなら、機械にやらせた方がよい。`A` キー。

決め方はこう。

1. **まず地と部品の差を見る。** 25 未満なら**合わせない**。
   部品が置かれていないか、照明が部品を洗っている。ここで無理に閾値を
   決めると平らな面のノイズを拾う（実測で、真っ白な紙に 890個の「部品」を
   見つけた）。合わせられない理由を文で返す
2. 閾値は大津に任せる。場ごとに正しい値が変わるので固定値は持たない
3. 連結成分の面積を大きい順に並べ、隣り合う**比**が 3倍以上のところで切る。
   差ではなく比を見る。部品どうしの差より、部品とノイズの比の方が大きい
4. 段差が無ければ、いちばん大きい塊の 20% を下限にする

| 場 | 大津 | 決まった MIN_AREA | 検出 |
|---|---|---|---|
| プロジェクター（部品210 / 紙243） | 228 | 373 | 2個 |
| 照らさない（55 / 190） | 130 | 122 | 2個 |
| モニタ（36 / 250） | 155 | 122 | 2個 |
| 何も置いていない紙 | — | **合わせない** | 0個 |

### 明るさの統計はパーセンタイルで測ってはいけない

はじめ `roi_stats` は暗い方 1% を「部品の濃さ」としていた。これは
**部品が占める面積の割合に振られる**。同じ場で ROI の広さだけ変えると:

```
パーセンタイル方式:   ROI を広く取ると部品が 1% に届かず、差が 33 → 12 に化けた
```

閾値を決める根拠がこれでは頼れない。大津は「2つの山に割る」ので、
割ったあとの**各クラスの平均**を取れば面積の割合に依らない。

| ROI | 部品 | 地 | 差 |
|---|---|---|---|
| 200x150 | 219 | 242 | 23 |
| 400x300 | 214 | 242 | 28 |
| 800x600 | 211 | 242 | 31 |

同じ場なら ROI をどう取っても同じ値が出る。面積比も併記するようにした
（`area 1.0%`）——これが 0.1% を切っていたら、そもそも部品が小さすぎる。

### 囲うのは文字ではなく紙

検出範囲を手で囲えるようにしたら、こんどは**狭く囲いすぎて**読めなくなった。
実機で 60x57 まで絞っていた。文字のまわりにぴったり寄せたくなるが、これは
三重に効いてくる。

1. **OCR に渡る画像がそのまま小さくなる。** Vision はテキスト行を探すので、
   数十画素の画には行を見つけない
2. **`PLACE_ZONE` が 72% を切り取る。** 60px 幅の ROI なら検出されるのは 43px
3. **`DROP_BORDER` が縁に触れた塊を捨てる。** 文字に寄せると部品そのものが
   縁を踏んで落ちる

だから囲うのは**紙の外周**。ROI を決めたとき、狭ければその場で理由つきで
警告を出すようにした（目安 300x300 以上、フレーム幅の 1/3 以上）。

あわせて `SCREEN_ROI` を `config.py` に持てるようにした。プロジェクター構成
では自動検出がまず当たらないので、毎回起動ごとに囲い直していた。数値で
固定できれば、ドラッグの当たり外れに左右されない。`W` キーは
`CAM_ZOOM` `CAM_CENTER` `OUT_RECT` `SCREEN_ROI` の4つをまとめて書き戻す。

### 「0個」には二種類ある

閾値が外れているのか、面積のふるいで落ちているのか、`parts 0` だけでは
区別がつかない。実機で ROI を 80x82 まで小さく囲ったまま `MIN_AREA = 800`
（ROI 面積の 17%）で閾値を 30回振り続ける、という時間を費やした。
通るのは 800〜1640px の窓だけなので、閾値が正しくても 0個のままだった。

`extract_parts` が**何個をどの理由で捨てたか**を返すようにした。

```
dropped: small 1  large 0  border 0   |  min_area 800 = 17% of ROI  <- too big, press [
```

読み分けはこう。

| 表示 | 意味 |
|---|---|
| `small 1` と出て `parts 0` | **塊は見えている。**面積のふるいが厳しい → `[` |
| 全部 0 で `parts 0` | **塊が見えていない。**閾値が外れている → `o` か `=` |
| `border` が多い | ROI の縁を部品が踏んでいる → 囲い直す |

`MIN_AREA` は画素数の絶対値なので、ROI の大きさに対して見ないと意味がない。
比率を併記して、8% を超えたら警告するようにした（目安は 1〜3%）。
`[` `]` の刻みも固定 100 では大小どちらの場でも合わないので、いまの値の
1/5 ずつ動くようにした。

なお ROI が小さいと OCR も痩せる（実機で 120x138 まで落ちた）。デジタル
ズームは画素を増やさないので、ここは `FRAME_WIDTH/HEIGHT` を 1920x1080 に
上げるか、カメラを物理的に寄せるのが正しい。

### プロジェクターは照らすほど検出を悪くする

モニタ構成がうまくいっていた理由は、**下から光っていた**ことだった。置いた
ものは光を遮る影絵になるので、部品 36 / 地 250 という気持ちのよい差が出る。
これは偶然ではなく、構成そのものが持っていた性質。

プロジェクターは上から照らす。**紙も部品も同じ光を浴びる**ので、黒い部品でも
表面が光を返す。実機で 3Dプリントの部品を白い紙に置いたときの実測:

```
ink 210/228   bg 243   gap 33
```

差 33。これは「黒いものを撮った」値ではない。照明が検出の敵に回っている。

| 構成 | 部品 | 地 | 差 | 大津 |
|---|---|---|---|---|
| モニタに黒い部品（下から光る） | 36 | 250 | 214 | 112 |
| プロジェクターで白を投げて照らす | 210 | 243 | **33** | 226 |
| 置く場に何も投げない（部屋の明かり） | 55 | 190 | 135 | 125 |
| 明るい部品を暗い布に（`DETECT_DARK = False`） | 215 | 60 | 155 | 133 |

差 33 でも、閾値をあいだ（225 前後）に置けば検出はできる。ぼかしを通すと
ノイズは 1/5 程度に落ちるので、33 あれば足りる。**が、余裕がない。**

効く手は2つ。

**置く場には何も投げない**（`CANVAS_BG = 0`）。部屋の明かりで紙を見れば、
部品は自分の色の暗さで写り、差が戻る。プロジェクターの仕事は出力だけになる。
そして光を足すことしかできないので、**描いたものが部品として拾われることが
原理的にない**——モニタ構成でいちばん苦労した自己検出が、ここでは消える。
`DRAW_MIN_LUMA` を守る必要もなくなる。副作用として `auto_screen_roi` は
効かなくなるので、ROI はドラッグで囲う。

**極性を逆にする**（`DETECT_DARK = False`）。明るい部品を暗い地の上に置き、
明るいものを部品とみなす。部品が明るい色で刷られているなら、白い紙と戦うより
こちらの方が素直。

どちらも「照らす／照らさない」と「明るい／暗い」の組み合わせを選び直して
いるだけで、**部品の albedo に対して地をどちらへ振るか**という一つの判断。

### 紙に書いたものを読むと、閾値の前提が変わる

`FIXED_THRESHOLD = 110` は**モニタの上に黒い部品を置いたとき**に測った値。
地 250・部品 36 なので、あいだの 110 できれいに割れる。

紙にペンで書いたものを上から撮ると、同じ数字がまったく効かない。
紙は白飛びせず（実測 205 前後）、ペンの線も真っ黒にはならない（150 前後）。
**どちらも 110 より明るいので、何も検出されない。**

| 場 | 線 | 地 | 大津が選ぶ値 | 固定110 |
|---|---|---|---|---|
| モニタに黒い部品 | 36 | 250 | 112 | 正しく効く |
| 紙にペン | 150 | 205 | 178 | **検出画素 0** |

固定 110 は、たまたまモニタ構成で大津が選ぶ値（112）と同じだった。
つまり最初から「その場での大津の答え」を焼き付けていたに過ぎない。
場が変われば答えも変わる。**紙に移すなら `o` で大津に切り替える**のが正解。

大津を既定から外した理由（ROI が画面の外まで含んでいると閾値が明るい側へ
引っ張られる）は、ROI を手で囲えるようになったいま、ほぼ消えている。

閾値を勘で動かさずに済むよう、確認ウィンドウに ROI の明るさの分布を出した。

```
ink 150/205   bg 205   otsu would pick 178   <- thr is outside ink..bg
```

`ink` が暗い方 1% と 5%、`bg` が中央値。**閾値がこのあいだに入っていなければ、
何も検出されないか全部検出されるかのどちらか**なので、外れているときは
橙で警告を出す。`-` `=` の刻みも 2 では遠すぎたので `THRESHOLD_STEP = 5` にした。

### ROI は元フレームの座標で持つ

ズームは**同じ場所を切り出し方を変えて見ているだけ**なので、検出範囲は
取り直すのではなく座標を変換して持ち越す。最初はズームのたびに
`auto_screen_roi` をやり直していたが、実機ではこうなった。

```
  カメラ  CAM_ZOOM = 1.70  CAM_CENTER = (0.640, 0.460)
画面 ROI = (12, 268, 407, 151)（自動）
  カメラ  CAM_ZOOM = 1.70  CAM_CENTER = (0.660, 0.460)
画面 ROI = (371, 42, 370, 370)（自動）      ← まったく別のものを掴んだ
```

寄せるキーを押すたびに検出範囲が飛ぶ。しかも**手で囲った範囲が
ズーム1回で捨てられる**ので、自動検出が当てにならない場でこそ使いたい
手動指定が、いちばん使えなくなっていた。

いまは `screen_roi` を元フレームの座標で持ち、毎フレーム切り出しの座標へ
変換して使う。ズームしてもパンしても同じ場所を指し続け、寄せすぎて画角の
外へ出たときだけ警告を出して画角全体に落とす。`r` の config 読み直しでも
ROI は触らない（config に入っていないので、捨てる理由がない）。

### ズームは切り出すだけで、拡大しない

`CAM_ZOOM` は**フレームを切り出すだけ**で、元の大きさに引き伸ばさない。
引き伸ばしても画素が水増しになるだけで、OCR に渡せる情報は増えないため。
出力ウィンドウは `WINDOW_NORMAL` なので、小さい画を渡せば同じ枠に拡大表示
される＝見た目はちゃんと寄る。**素の画素のまま OCR にかかる。**

`CAM_TRY_OPTICAL` でレンズの光学ズームも試せる（効けば画素が実際に増えるので
そちらが良い）が、macOS の AVFoundation 経由では **まず効かない**。
`set` は成功を返すのに `get` が変わらないので、`get` で確かめてから信じる。
起動時に効いたかどうかを出す。

### 写す範囲は最後に一度だけ写し込む

描画のコードは `OUT_RECT` を一切知らない。1920×1080 の画面をこれまで通り
描いて、**最後に `fit_output` で範囲の中へ収めるだけ**。だから位置合わせを
何度やり直しても中身の作りには影響しない。矩形なら縮小して貼るだけで
2〜6ms、4隅指定（`OUT_CORNERS`）の透視変換でも 8ms。

副産物として、**位置合わせが検出の較正も兼ねる**。範囲の外は黒＝投影されない
ので、カメラから見て明るい領域はちょうど写した範囲になる。`auto_screen_roi`
は「フレーム内で最大の明るい塊」を探しているので、これをそのまま拾う。

台形補正（`OUT_CORNERS`）は**プロジェクター本体で追い込めない残りを詰める用**。
こちらで歪めると、カメラ座標から画面座標への対応（`roi_pt_to_canvas` の
線形近似）がそのぶん狂う。本体の補正を先に使うこと。

### 濃淡が反転する

**プロジェクターは光を足すことしかできない。** 黒を投げても投影面の色が
そのまま見えるだけで、暗くはならない。だから定着の場の `FIX_INK`（暗いインク）
は**プロジェクターでは見えない**。地と字を入れ替える必要がある。

```python
FIX_INK       = (245, 245, 245)   # 光がインクになる
FIX_LABEL_INK = (150, 170, 190)
FIX_BG        = 0                 # 地は「投げない」＝投影面のまま
CANVAS_BG     = 255               # 置く場は投げ続ける（検出の地になる）
```

置く場の白は残す。投影面を白く照らすことが、そのまま部品との明暗差になる。
ここだけはモニタと同じ理屈で効く。`config.py` の写す範囲の節の末尾に
この値を書いてあるので、入れ替えて `r`。

いっぽうで**モニタで苦労した自己検出は、プロジェクターでは軽くなる**。
暗い色を投げても暗くならないので、描いたものを部品として拾いにくい。
輝度の下限（`DRAW_MIN_LUMA`）の制約が効くのはモニタ構成の方。

## 操作（probe_ocr.py）

| キー | 動作 |
|---|---|
| `1`〜`6` | いま組んでいる字を選ぶ |
| （自動） | **手を止めて 1.2秒で1回だけ判定**。配置を変えるまで再判定しない |
| `t` | 自動／手動（SPACE のみ）の切り替え |
| `SPACE` | いますぐ判定 |
| `q` | 終了して正解率を集計表示 |

## 認識の対象

部品数の少ない順。**1部品で成立する字があるのは想定内。**

| 字 | 部品数 | 備考 |
|---|---|---|
| つ | 1 | 曲線1個。部品そのものが字 |
| う | 2 | **つ ＋ てん**。点を1個足すだけで字が変わる＝最小の見せ場 |
| い | 2 | |
| よ | 3 | 下部のループ部品が要る |
| は | 3 | |
| ほ | 4 | **は ＋ よこせん1本** |

「どの字が何個の部品でできているか」という階調が、そのまま内容になる。

## 設計判断

### 方眼は出さない

検出のために画面へ方眼を出す案があったが、**要らなくなった**。白一色なら
固定閾値で通るし、方眼線はむしろ部品として誤検出される。

組み立てガイドとしても出さない。理由はこれ。

> **方眼を出すと、機械が丸める前に、人間が自分で揃えてしまう。**

見せ場は「あなたの配置」と「規格」の差なのに、ガイドを出すとその差が
入力前に潰れる。作業領域を示す**外枠だけ**にして、内側の升目は引かない。

較正用のチェッカーは Step 3 で使うが、**較正の瞬間だけ表示して消す**。

### 認識部は1関数に隔離する

```python
def recognize(mask) -> tuple[str, float]:
    """組み上がったマスクを受け取り、(文字, スコア) を返す"""
```

**macOS 純正 OCR（Vision）が本命。IoU 照合は参考値として併記するだけ。**

一度は IoU に倒したが、次の理由で戻した。

> **飾らない技術から生まれる誤読に価値がある。**

IoU の誤読は**こちらが設計した尺度の産物**（正規化の仕方・回転幅・IoU という
距離の選び方）で、外から来た誤読ではない。OCR は**この作品のために作られて
いない無関心な読み手**で、想定外の入力に出会って外す。その誤読は本物。

精度で OCR を捨てる理由も無くなった（下の「2字にすると直る」を参照）。

### 加工は切り出しだけ

二値化して白地に描き直すより、**生のグレースケールをそのまま渡す方が成績が
良い**（実測 4/6 対 3/6）。硬い縁がラテン文字に見えるらしく `つ` が `C` になる。

つまり **画像として抜いて OCR に渡すだけ** が、いちばん簡単でいちばん良い。
輪郭抽出は「静止したか」「どこに置かれたか」を知るためにだけ使う。

読めなければ **「読めず」と出す**。無理に何かを返さない。読めなかったことも結果。

### 読めなければ何もしない

一度は「静止時間だけで光が育って定着する」と作ったが、それだと
**OCR が読めなくても痕跡が定着してしまう**。見出しのない痕跡が出るのは
設計が破れている証拠だった（`FIX_UNREAD` という設定が存在したこと自体が徴候）。

いまは読みが通ってからしか進行しない。**読めないものには何も起きない。**
機械は無関心で、こちらが動かして試すしかない。

`REREAD_SEC` を 0 より大きくすると、読めなかったとき再挑戦する。
既定は 0（再挑戦しない）。

### 静止判定は許容差つきで

重心を量子化して完全一致を見ると、**境界をまたぐノイズで誤って「動いた」**
になり、進行がリセットされ続ける。`POS_TOL` の許容差つきで比べている。

配置が動くたびに `arr_id` が増え、読みと定着はこの id に紐づく。
同じ配置を二度読まない／二度定着させないのはこれで保証している。

## つまずいた点

### 1. モニタを寝かせても干渉問題は消えていない

プロジェクタを捨てれば赤外カメラが要らなくなる、までは正しい。
ただし**カメラは上から「部品」と「画面の表示」の両方を見る**ので、
背景差分をするなら場所が変わっただけで同じ構造で壊れる。

この構成では**画面を白一色の既知の背景に固定する**ことで回避した。
つまり干渉が消えたのではなく、**干渉が計算可能になった**。

### 2. ROI を切らないと大津が効かない

画面の外（机・部屋）がフレームに入っていると、大津の閾値は
「明るい画面 vs 暗い机」の間で割れる。部品と画面の差ではなくなるので
何も拾えない。**ROI で画面領域だけを切るのが必須**で、ここが一番効く操作。

### 3. モアレ

カメラの画素と液晶の画素が干渉して縞が出る。二値化の前に
`GaussianBlur` を入れればほぼ消える。カーネルは `config.py` の `BLUR_KERNEL`。

### 4. 大津の閾値が明るい側に引っ張られる

実機で **thr=183** まで上がり、画面の明るさムラまで部品として拾った。
大津は2つの山が同じくらいの大きさであることを暗に仮定するが、
**部品は画面面積の数%しかない**ので、境界が明るい側へずれる。

部品は真っ黒・画面は真っ白とはっきり分かれているので、**固定閾値（110）**
の方が確実だった。あわせて **ROI の縁に接する塊を捨てる**フィルタを入れた。
画面に置いた部品は縁に触れないので、触れているものは画面の縁・ベゼル・
明るさムラだと判断してよい。これで縁のノイズが自動で消える。

### 5. Vision は「テキスト行」を探している

正方形のキャンバスの中央に1文字だけ置くと、Vision はそもそも文字として
検出しない（confidence 0.00 で結果が空）。**キャンバスを横長にすると跳ねる。**

同じ字・同じ隙間で比較した実測:

| キャンバス | つ | う | い | よ | は | ほ | 計 |
|---|---|---|---|---|---|---|---|
| 正方形 512 余白18% | × | × | × | × | ○ | × | **1/6** |
| **横長 1024×384 余白8%** | × | × | ○ | ○ | ○ | ○ | **4/6** |

あわせて分かったこと。**隙間は OCR を壊さない**（`は` は3箇所に隙間を
入れても読めた）。壊しているのは字の単純さで、**つ と う はどの条件でも
検出されない**。線に見えて文字に見えないためと思われる。

なお `setMinimumTextHeight_` は Swift 側で落ちる（Python の try では
捕まえられないクラッシュ）ので使わない。

### 6. OCR と IoU を同条件で比べた

フォントから描いた字を、部品に割って少しずつずらし（＝手で緩く組んだ状態）、
傾きも加えて、崩れ具合を4段階に振って測定した。

| 条件 | OCR | IoU（スコア範囲） |
|---|---|---|
| きれい | 4/6 | **6/6**（0.95–0.99） |
| 少し崩す | 3/6 | **6/6**（0.79–0.96） |
| 崩す＋傾ける | 3/6 | **6/6**（0.74–0.90） |
| かなり崩す | 3/6 | **6/6**（0.41–0.96） |

**IoU は 24/24。** そして狙いどおり、崩すほどスコアが下がる
（`ほ`: 0.98 → 0.86 → 0.74 → 0.41）。「規格からどれだけ遠いか」が数値になっている。

実機でも同じ傾向だった。**読めたのは `は`（conf 0.50）だけ**で、
`ほ`・`い`・`つ` は読めず、`う` は `C/` と返った（曲線を C、点を / と読んだ）。

### 7. 1字だと読まれない。2字にすると直る

Vision は「テキスト**行**」を探す設計なので、**1字では行として成立しない**。
横に文脈が無いと拾わない。Preview の Live Text では読めたのに手元のコードで
落ちていたのも、Preview には周囲の文脈ごと渡っていたため。

同じ崩し方で字数だけ変えた実測:

| 字数 | 正解率 |
|---|---|
| 1字 | 3/6 |
| **2字** | **6/6** |
| **3字** | **6/6** |
| 4字以上 | 5/6 |

**2字並べるだけで完全に直る。** 唯一外したのは `ほほほほ` → `¥11¥1¥1` で、
**同じ字の繰り返し**は苦手らしい。

> 実務上の制約：2字同時に組むには**部品セットが2組**必要。
> `はは` なら は の部品が2つずつ要る。

### 8. 輪郭から描き直すと、リングの穴が埋まる

`findContours(RETR_EXTERNAL)` は外周だけを返すので、そこから `fillPoly` で
マスクを描き直すと「わ」や半濁点の**○の穴が埋まる**。定着させたいのは形その
ものなのに、**穴のない塊が定着してしまう**という実害が出た。

直し方は「描き直さない」。`extract_parts` が返すマスクは連結成分から作られて
いるので**穴は最初から正しく空いている**。置く場の矩形へ拡大するだけでよい。
輪郭を経由していたのが余計だった（`roi_to_canvas` もこれで不要になった）。

副作用として、距離変換の光が**穴の内側にも回り込む**。インクが字の内側へ
滲んだように見えるので、これは残してある。

なお `contourArea` の方は依然として穴を含んだ値を返すので、**面積で部品を
同定しようとすると外す**。ゴミ取りの `MIN_AREA` は連結成分の面積
（`CC_STAT_AREA`）を見ているので、そちらは正しい。

### 9. 重複の抑止を配置で判定すると、部品数の揺れですり抜ける

同じものが二度反応・二度定着するのを止めるのに、はじめは「前回の配置と
近いか」で判定していた（`REFIX_TOL`）。定着の側はこれで止まる。

絵文字の側は止まらなかった。実機ログ:

```
読めた: すし 1.00   部品3個   → 🍣
読めた: すし 0.50   部品2個   → 🍣
読めた: し   0.30   部品1個
読めた: すし 1.00   部品2個   → 🍣
読めた: すし 1.00   部品3個   → 🍣
```

同じ「すし」を置いたままなのに4回出た。原因は `moved()` が**部品数が違えば
即 True を返す**こと。閾値の際にある部品は 3→2→1→2→3 とちらつくので、
配置での判定はそのたびに「別の配置だ」と言う。`REFIX_TOL` をいくら大きく
しても、距離の問題ではないので効かない。

そこで絵文字だけは**語と時間で止める**（`EMOJI_COOLDOWN_SEC`）。配置を一切
見ないので、部品数がどう揺れても関係ない。さらに、読み続けているあいだは
時刻を更新して**クールダウンを延ばす**。上のログを再現すると 4回 → **1回**。
片付けるか別の字にして間が空けば、また反応する。

定着の側は配置での判定を残している。あちらは「同じ場所に二枚重ねない」と
いう空間の話なので、判定も空間でよい。**同じ「二度やらない」でも、止める
理由が違えば見る軸も違う。**

### 10. 何も置いていないところにも、OCR は文字を見つける

プロジェクターの実験に移した初日、こうなった。

```
画面 ROI = (38, 21, 1204, 678)
  読めた: IAT8 0.30   部品1個
  読めた: -”AT8 0.30   部品3個
  定着: 「-”AT8」（1枚目）
```

ROI がフレームほぼ全部になっている。`auto_screen_roi` は「フレーム内で最大の
明るい塊」を探すが、**プロジェクターだと投影面がいちばん明るい塊になるとは
限らない**。部屋が明るければ壁も机も同じくらい明るく、境目が出ない。
そうなると部屋の暗いものを部品として拾い、Vision はそこに文字を見つける。

対処を2つ入れた。

**手で ROI を囲えるようにした。** `probe_contour.py` にはドラッグでの指定が
あったのに、`main.py` には自動検出（`a`）しかなかった。モニタなら自動で
足りていたので気づかなかった。確認ウィンドウの上でドラッグすれば決まる。

**仮名でない読みを捨てる**（`READ_CHARSET = "kana"`）。誤読そのものは残したい
——崩れた「ほ」が「ま」になるのはこの装置の見せ場なので——が、ここで落ちて
いるのは**そもそも部品を見ていない読み**の方。仮名を組む装置なので、仮名で
ない答えが返ったときは「置いたものを見ていない」と判断してよい。
`"jp"`（かな＋カタカナ＋漢字）と `"any"` にも切り替えられる。

確信度では分けられなかった。この幻視はどれも 0.30 だが、実機で正しく読めた
「すし」も 0.30 のことがある。**確信度は「読めているか」を測っていない。**
何を読んだかで判断するしかない。

### 11. 「全部どけた」は一瞬の 0 で判断してはいけない

どけたときは定着の抑止も絵文字のクールダウンも解ける——次は同じものでも
定着してよいし、反応も出してよいから。それを毎フレーム「部品が 0 個か」で
見ていた。実機でこうなった。

```
読めた: なつ 0.30   部品4個
  → 🌻 が流れる
定着: 「なつ」（3枚目）
読めた: なつ 0.30   部品4個
  → 🌻 が流れる          ← クールダウン6秒のはずが再発火
定着: 「なつ」（4枚目）    ← 同じ語が2枚
```

置いたままなのに、間で検出が一瞬 0 になっていた（同じログに「読めず（部品1個）」
が連発している＝際にいる）。そのたびに抑止が全部外れる。

**同じ形の失敗を3回繰り返している。**

| 回 | すり抜けたもの | 抑止の根拠 |
|---|---|---|
| 1 | 部品数のちらつき | 配置の一致（`POS_TOL`）|
| 2 | 部品数のちらつき | 配置の一致（`REFIX_TOL`）|
| 3 | 部品数が一瞬 0 | 部品の有無 |

毎回、**瞬間の値を根拠にしていた**のが原因。検出は際でちらつくものなので、
状態を切り替える根拠には「続いたこと」を使う。1回目は `MOVE_CONFIRM_SEC`、
2回目は語と時間のクールダウン、3回目が `CLEAR_CONFIRM_SEC`。

あわせて、解いた瞬間だけログに出すようにした。

```
  全部どけた（定着と反応の抑止を解いた）
```

**これが出ていないのに同じものが二度定着したら、原因は別にある。**
次に同じ症状を見たとき、1回で切り分けられる。

## 読めた語への反応（絵文字）

読めた語が対応表にあれば、絵文字が2秒だけ流れる。**恣意的に決めた6語だけ**。

```
うし → 🐄    なし → 🍐    なつ → 🌻
あい → ❤️    くり → 🌰    よい → 👍
```

完全一致のみ。`うしは` のような誤読では出ない（3字以上だと複数の語が同時に
一致して曖昧になるため）。**誤読は定着欄の見出しに残る**ので、絵文字の側は
正確な報酬にして混ぜない。

当たりを主役に、`EMOJI_OTHERS` の割合で残り5つの絵文字を混ぜて散らす。
**0 にすると当たりの絵文字だけ**になる（実測 14/14個が当たりになる）。

### OS の絵文字検索も作ったが、既定では使わない

`emoji_search.py` は macOS の絵文字ピッカーが使っている索引をそのまま読む。
手書きの辞書が要らず、語彙は OS が持っているもの。`EMOJI_SOURCE = "os"` で切替。

```
うし → 🐮🐂🐄    ねこ → 🐈😹😊😿    とり → 🪽🐦🕊️🐤🦃🦢🦜🪹
```

**ただし制御できない。** 完全一致が無い語は部分一致の段まで落ちて
`やま → 💩` のようなものが出る。展示で狙った反応を出すには、恣意的に
決めた対応の方が扱いやすい。だから既定は `"dict"`。

索引の作りは `emoji_search.py` の冒頭に書いてある（文書ID→絵文字の直接の表が
私有バイナリ `emoji.dat` の中にあって読めないので、**名前の突き合わせ**で
解決している。1,399/1,878 の文書に絵文字が付き、2字のかなは 92% が解決）。

### 輝度の制約をどう越えたか

絵文字は置く場に描くので本来は閾値に当たる。白側へ持ち上げれば安全だが、
実測で 🐄 と 🌻 は係数 **0.33** まで薄まり、何の絵文字か分からなくなる。

そこで既定は **反応中だけカメラを信じない**。直前の検出結果を保持して、
絵文字を部品として拾わないようにする。時間の方は進み続けるので定着は止まらない。
確認ウィンドウに `REACTING (camera ignored)` と出る。

`EMOJI_FULL_COLOR = False` にすると持ち上げ方式（検出を止めない）に切り替わる。

### 称号

見つけた語数で称号が付く。**活版の職階**から取っている
（文選工＝活字を拾う人、植字工＝組む人）。`config.py` の `TITLES`。

拾い手(1) → 文選工(2) → 植字工(3) → 組版工(4) → 校正者(5) → 活字守(6)

**語の一覧はどこにも出さない。** 何が入っているかが見えると探す面白さが消える。
出るのは見つけた数と称号だけ。

## ページ出力

`main.py` は判定のたびに結果を **http://localhost:8899** のページへ流す。
標準ライブラリだけの SSE（Server-Sent Events）で、WebSocket ライブラリは使わない。

ページに出るもの:

| 表示 | 出どころ |
|---|---|
| 大きな字 | **OCR が読んだ文字列**。読めなければ「読めず」 |
| 読み手の確信度 | OCR の confidence |
| 形として近い字（参考値） | **IoU 照合**の上位3つ。OCR とは別の読み手なので、食い違うことがある |
| 置かれた部品 | 検出した部品の数 |
| 下の行 | 読まれた字が積み上がっていく。組み直すたびに1字増える |

読めなかったときはページにも何も流さない（置く場と同じく無反応）。

出どころの違う2つを並べているので、**ラベルでどちらの数字かが分かるようにしてある**。

ファイルは `page_server.py`（stdlib のみ）と `page/index.html`（単一ファイル）。
